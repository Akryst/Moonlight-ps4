# ETS2 / TruckersMP: measurements and build 01.32

## Baseline from the live PS4

The user played ETS2 through TruckersMP using Sunshine's Desktop app. Desktop
is appropriate for this launcher. No host or console session was restarted
during capture. Anonymous GoldHEN FTP supplied `/data/moonlight/debug.log`
and the console configuration, saved locally under ignored `tools/ets2-analysis/`.
The analyzer selects the last active stream, excluding older sessions.

Configuration: original PS4, Ethernet, 1920x1080, target 60 FPS, 20,000 kbps
client budget, hardware decoding, Balanced (depth 2), four BGRA workers,
cached framebuffers. Sunshine reports H.264 AMF, SDR Rec.709, MPEG range,
display/capture cadence 59.9401 Hz and encoder bitrate 14,988,000 bps.
Client budget and actual encoder bitrate are different quantities.

The initial interval includes stream priming and reports 44.7 FPS; it is not
evidence that gameplay dropped to that value. There are subsequent slower
periods, so the whole session cannot be described as stable 60 FPS. The last
roughly three minutes average about 59.9 FPS with very few local drops.
These are client counters, not an independent measurement of physical screen
scanout, game simulation FPS or frame-by-frame input latency. A zero gap
counter does not prove the absence of all network loss or recovery.

## Implemented changes

1. **Color correctness.** The negotiated stream is Rec.709 limited, but the
   BGRA scalar and SSE2 paths previously used Rec.601/full-range coefficients.
   Both now use the same fixed-point Rec.709 limited-to-full conversion.
   Signed SSE2 high-product arithmetic avoids truncating intermediate products.
   The reference is [ITU-R BT.709](https://www.itu.int/rec/R-REC-BT.709):
   8-bit nominal luma black 16 / white 235 and neutral chroma 128.
   Tests compare against independent floating-point equations, black/white,
   saturated color bars, extremes, and scalar/SSE2 agreement.
2. **Presentation scheduling experiment.** Balanced allows up to 8 ms to wait
   for a free display buffer rather than the previous 4 ms. Low latency retains
   4 ms. This gives arrival jitter more room before abandoning a decoded frame;
   occupied framebuffers remain protected. Under contention it can add up to
   4 ms of permitted waiting; scheduler delays can exceed requested sleeps.
   A gain is plausible but has not been measured on the console with 01.32.
3. **Queue diagnostics.** Every 60 BGRA kick attempts, `present_queue` reports
   samples, waits, average/maximum wait, no-free-buffer drops and flip-submit
   failures. This distinguishes slot starvation from other local discard paths.
   The analyzer summarizes these fields when present.

There is no sharpening filter in the active 1080p BGRA path. The decoder's
1088-line allocation is cropped to 1080 visible lines and displayed at 1:1.
The color mismatch is confirmed by source and host logs; it does not establish
the cause of perceived sharpening. No console pixel capture was analyzed.

## Validation

Host tests passed with address/undefined-behavior sanitizers, including the new
color tests. The OpenOrbis build and PKG generation completed successfully.
The PKG is `dist/Moonlight-PS4-01.32-test.pkg`; `dist/SHA256SUMS` identifies it.

After finishing the current game, install 01.32 and repeat a comparable route
via Desktop with 1080p60, 20 Mbps, Hardware decoding, Balanced, Performance
overlay and File logging. Compare the image and retrieve the next log.
Use `python scripts/analyze_stream_log.py <debug.log> --output <report.json>`.
Compare sustained FPS, drops, callback cost and the new `present_queue` fields.
If waiting grows without improving drops, retain the color correction and
revert the scheduling experiment. No sustained 60 FPS guarantee is established
by host tests or packaging.
